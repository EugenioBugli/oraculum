# Operations workspace

Open **Operations** from the Session menu on Field or Dashboard, or from Fleet. The page provides read-only diagnostics and optional authenticated build, staging, deployment/rollback, service and network workflows. See [configuration, permissions, recovery and verification](OPERATION_JOBS.md). No operation runs on page load; motion stays in the robot control pane.

Targets are allowlisted in `config.yaml` under `operations.targets`, which ships as a commented example and defines no target by default. One entry describes one robot: its factory wired address and subnet, the SSH user and service, the model, the player number, the board layout, the fixed gateway address on that subnet, and the local framework checkout the artifact comes from. Recheck identity, model, board layout, and gateway address before any deployment. Only one robot should be attached to that factory-address Ethernet segment at a time. Other targets need a confirmed model, player number, and board layout before staging.

The page always shows the gateway's IPv4 interfaces, whether one is on the configured robot subnet, and current robot telemetry with packet ages. **Run read-only SSH probe** checks TCP 22, then uses SSH batch mode with strict host-key checking and a five-second timeout. It reads service active state, installed version, `/dev/input/js*`, and the latest 30 service log lines. A disconnected robot, unknown host key, or absent SSH key produces an explicit failure; no password prompt or remote write is attempted.

The command map shows the currently supported paths for STOP, Resume, DAMP, Get up, Go to, and manual movement. It shows the selected robot's reported model, state, latch, version and packet age; the direct controls link appears only when fresh command-capable debug telemetry matches the configured address, player number, and model, and the gateway is in practice mode. A blank latch may also mean old firmware did not report one. Sit and Lie down are unavailable on the current framework port. The map itself sends no command.

SSH diagnostics and artifact preview require the gateway to be started with `ORACULUM_ACCESS_TOKEN` and opened through its existing access link. The SSH probe is additionally disabled in match mode. The browser does not store a robot password. Do not put an access token in `config.yaml` or commit it.

**Preview artifact** reads the local robot checkout configured for the selected `operations.targets` entry (falling back to `fleet.repo`). It reports the Git commit/dirty state, AArch64 binary architecture and SHA-256, and only the proposed `robot`, `oraculum`, `oraculumHost`, `useRerun`, `useGameController`, and `customMode` values. Wi-Fi credentials and unrelated config are excluded. A missing build, unknown target model, wrong architecture, dirty checkout, or missing intended gateway subnet address blocks staging. Preview performs no build or robot transfer.

Once those checks pass, a local terminal can pin the existing build without contacting the robot:

```bash
python3 tools/stage_artifact.py --target robot6 --profile practice
```

The staged binary, complete `config/` tree, `version.txt`, and manifest live in ignored `artifacts/<commit>-<binary-hash>-<config-tree-hash>/`, with restrictive permissions. The bundle sets player number and board layout in `deploy.yaml` and `scenario: real` in `deploy.yaml` (or legacy `settings.yaml`). Repeating the command verifies the existing copy; a mismatch fails. The staging tool excludes Wi-Fi settings and refuses other secret-looking YAML fields and ignores only Pixi's untracked `.pixi-cache/` output in the source cleanliness check. The authenticated Stage workflow uses this same implementation. Staging can use a configured intended laptop address while Ethernet is disconnected; activation later requires that address to be live on the interface.

On 2026-10-26 the existing 347,795,136-byte ARM binary from source commit `bc462d43` was staged locally with its full config as `bc462d4327f6-8e0f3dd4a8c3-144392754ea9` and passed the offline deploy review. The earlier incomplete bundle was removed. The binary hash pins the bytes; its source commit records the clean checkout, but does not attest the build history.

After staging, **Wired deployment review** lists the local artifacts and rechecks the binary and every config file hash, target identity, model, player number, board layout, profile, and intended gateway address before showing the proposed activation and rollback sequence. Execution is available separately through the authenticated workflow after preview and support confirmation. The UI also reports whether the intended gateway address is currently active on Ethernet. Its read-only SSH probe currently needs key authentication; the robot was deployed through a separate password-authenticated wired session.

Historical hardware result (not current robot state): robot 6 received TCM over Ethernet later on 2026-10-26. The original staged binary failed against the robot's newer Rerun SDK, so the active binary has a private compatibility library path; a missing detector model was also installed. At that test, both services were active and Oraculum received fresh robot 6 telemetry. The exact derivation, failed attempts, rollback path, and checks are in the operator's own deployment record, which is kept outside this repository. Physical motion and camera acceptance remain open. The authenticated wired adapter now implements build/stage/deploy/rollback and service jobs independently of the older Wi-Fi deployment script. It has offline verification but has not deployed the newly ported framework onto a robot.
